# Requirements Analysis

**Stage:** requirements-analysis
**Intent:** 261118-ai-job-enhancement
**Date:** 2026-11-18
**Project type:** Brownfield — extending the AIventure MVP

---

## Intent Analysis

This intent extends the existing AIventure remote-job matching platform with two in-scope capabilities:

1. **Improved CV Parsing (non-LLM)** — improve the accuracy of the heuristic skill and job-title extractor (`extractCriteria.ts`) using an expanded static dictionary and better title-extraction logic. No LLM integration in this intent.
2. **QA Validation Layer** — systematic quality assurance of the matching engine: golden-dataset regression tests, property-based tests for scoring invariants, and a requirements traceability matrix.

LLM-assisted CV parsing and AI-assisted job matching are explicitly **out of scope for this intent** and deferred to a future intent.

The existing app is a working Next.js 16 App Router application with 289 passing tests. All new work is additive — no changes to the API route, the UI structure, or the data model.

---

## Functional Requirements

### FR1: Enhanced CV Parsing (non-LLM)

**Description:** The system shall improve skill and job-title extraction from uploaded CVs using an expanded static dictionary and improved heuristics, without introducing any LLM dependency.

**Acceptance Criteria:**
- Given a CV uploaded by the user
- When parsing completes
- Then the extracted skills list covers more technology skills than the current ~120-entry dictionary
- And the extracted job titles reflect role names from the CV more accurately than the current label-pattern approach

#### FR1.1: Expanded Skills Dictionary
**Description:** The skills dictionary (`skills-dictionary.ts`) shall be expanded to cover a broader set of technology skills.

**Acceptance Criteria:**
- Given the current `skills-dictionary.ts` with ~120 entries
- When the enhancement is applied
- Then the dictionary contains at least 200 distinct skills across languages, frameworks, databases, cloud/DevOps, AI/ML, data, and testing tools
- And skills with common aliases (e.g., "React" and "React.js", "Postgres" and "PostgreSQL") are normalised to one canonical entry so both forms match

#### FR1.2: Improved Job Title Extraction
**Description:** The job title extractor shall recognise role history entries by proximity to date ranges rather than relying solely on a fixed list of label patterns.

**Acceptance Criteria:**
- Given CV text containing a role history entry such as "Senior Software Engineer at ACME (2022–2024)"
- When `extractJobTitles()` runs
- Then "Senior Software Engineer" is included in the returned titles
- And extracted titles are deduplicated and normalised to title case
- And the existing golden test in `improve-cv.test.ts` remains green

---

### FR2: QA Validation Layer

**Description:** The system shall have a systematic QA layer for the matching engine: golden-dataset regression tests, property-based tests for scoring invariants, and a traceability matrix linking every requirement to at least one test case.

**Acceptance Criteria:**
- Given the matching engine codebase
- When the QA layer is applied
- Then every FR and NFR in this document has at least one automated test case or a documented not-covered entry
- And the existing 289-test suite remains green
- And CI enforces 80% line-coverage (affirmed in Practices Discovery)

#### FR2.1: Expanded Golden Dataset
**Description:** The existing §7.5 golden test (`score.test.ts`) shall be supplemented with a broader set of job+criteria fixtures covering diverse scoring scenarios.

**Acceptance Criteria:**
- Given a golden dataset of ≥10 job+criteria pairs stored in `web/tests/fixtures/golden-scoring.json`
- When `scoreJob()` runs against each pair
- Then each job scores within ±2 percentage points of its expected `matchPercent`
- And the dataset covers: all-active-factors job, zero-criteria job (expects 100%), salary-only match, timezone-only match, and benefit-heavy match

#### FR2.2: Property-Based Tests for Scoring Invariants
**Description:** Property-based tests shall verify that the scoring engine satisfies key invariants for any valid input.

**Acceptance Criteria:**
- Given random valid `Job` and `Criteria` inputs generated by a property-based testing library (no preference — use whatever integrates cleanest with Vitest)
- When `scoreJob()` runs
- Then `matchPercent` is always an integer in [0, 100]
- And a job with zero active criteria always scores 100
- And `rankJobs()` output is always sorted descending by `matchPercent`, ties broken by `publishedAt` descending

#### FR2.3: Requirements Traceability Matrix
**Description:** A traceability matrix shall link every FR and NFR in this document to at least one test case.

**Acceptance Criteria:**
- Given the requirements in this document
- When the QA traceability matrix is produced
- Then every FR and NFR has a row with: requirement ID, description, test case ID or file, status (Covered / Not Covered)
- And the matrix is stored at `qa/traceability-matrix.md`
- And any Not Covered item has a documented rationale

## Non-Functional Requirements

### NFR1: Test Coverage Floor
**Target:** 80% line-coverage maintained across the whole `web/src/` tree after all new code is added.

**Acceptance Criteria:**
- Given all new modules added by FR1 and FR2
- When the full test suite runs in CI
- Then total line coverage is ≥ 80%
- And no existing test is modified to lower a threshold

### NFR2: Accessibility
**Target:** Any new UI elements introduced by this intent (e.g., updated CV confirmation dialog) meet WCAG 2.2 Level AA.

**Acceptance Criteria:**
- Given new or modified UI components
- When tested with axe-core
- Then zero new violations
- And behaviour is consistent with the existing dashboard accessibility pattern

### NFR3: Backward Compatibility
**Target:** No change in observable behaviour for users who do not use the CV scanner.

**Acceptance Criteria:**
- Given a user who never uploads a CV
- When they use the application after this intent is merged
- Then ranking, filtering, and all UI features behave identically to the pre-enhancement version
- And no new required configuration is introduced

## Constraints

### C1: Technology Stack (unchanged)
Next.js 16, TypeScript strict, MUI v9, Vitest — no new dependencies unless required by FR2.2 (property-based library).

### C2: No LLM in this intent
No LLM API calls, no AI provider SDK, no server-side proxy for ML inference. Deferred to a future intent.

### C3: Existing API Terms
Himalayas and Remotive ToS remain in force. No change to the data pipeline.

### C4: Test Coverage Floor
80% line-coverage in CI (affirmed in Practices Discovery). All new code must be testable with the existing Vitest + jsdom setup.

---

## Assumptions

### A1: Existing Tests Remain Green
All 289 existing tests pass unmodified after the enhancements are applied.

### A2: CV Parser Gap Accepted
`parseCv.ts` has a known untestable gap (browser API coupling: `File`, `GlobalWorkerOptions`, dynamic imports). This gap is documented and not addressed in this intent.

### A3: Skills Dictionary Is Static
The expanded dictionary is a hand-curated static TypeScript file. Dynamic or LLM-driven expansion is out of scope for this intent.
